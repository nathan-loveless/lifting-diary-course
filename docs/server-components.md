# Server Component Coding Standards

These standards apply to all server components (pages, layouts and any other async server component) throughout this project.

## 1. `params` MUST Be Awaited

**In Next.js 15+, `params` is a Promise. It MUST ALWAYS be awaited before any of its values are accessed.**

- Never read `params.workoutId` directly. Never destructure `params` in the function signature. Await it first.
- This rule applies to every server component that receives `params`: `page.tsx`, `layout.tsx`, `generateMetadata`, and so on.
- Because `params` is a Promise, the component that reads it must be `async`.

```tsx
// Good
export default async function Page(props: PageProps<"/dashboard/workout/[workoutId]">) {
  const { workoutId } = await props.params;
  // ...
}

// Bad: params is a Promise, so workoutId is undefined
export default function Page({ params }: { params: { workoutId: string } }) {
  const { workoutId } = params;
}
```

### Typing

- Type the props with the globally available `PageProps<"/route">` helper (or `LayoutProps<"/route">` for layouts) rather than hand-writing the params type. The route types are generated by `next dev` / `next build`; run `npx next typegen` if a new route is not recognised.
- If you pass the promise down to a child component, type it as `PageProps<"/route">["params"]`.

### Dynamic rendering and `<Suspense>`

Awaiting `params` is request-time data. This project follows the existing page pattern: the default export is a synchronous shell that wraps an async content component in `<Suspense>`, and the content component awaits `params`:

```tsx
export default function EditWorkoutPage(
  props: PageProps<"/dashboard/workout/[workoutId]">,
) {
  return (
    <Suspense>
      <EditWorkoutContent params={props.params} />
    </Suspense>
  );
}

async function EditWorkoutContent({
  params,
}: {
  params: PageProps<"/dashboard/workout/[workoutId]">["params"];
}) {
  const { workoutId } = await params;
  // ...
}
```

## 2. `searchParams` MUST Also Be Awaited

`searchParams` is a Promise in the same way as `params`, and it MUST be awaited before use.

```tsx
const { date } = await searchParams;
```

## 3. Treat `params` and `searchParams` as Untrusted Input

- Values from `params` and `searchParams` are plain user-controlled strings. Validate them (for example with `zod`) before use, and call `notFound()` when a route param is malformed.
- Never use them to identify the current user. The user ID always comes from Clerk on the server (see `docs/auth.md`).
- Any record looked up by a route param must still be scoped to the logged-in user (see `docs/data-fetching.md`).

## 4. Other Server Component Rules

- Server components are `async` functions and fetch data by calling helpers from `src/data/` (see `docs/data-fetching.md`). They must not query the database directly.
- Do not add `"use client"` to a page or layout. Push interactivity down into a small client component and pass data to it as props.
- Do not use client-only hooks (`useState`, `useEffect`, `useRouter`, and so on) in a server component.
- Verify the user inside every protected page with `auth.protect()` (see `docs/auth.md`).

## Checklist

- [ ] `params` is awaited before any value is read from it
- [ ] `searchParams` is awaited before any value is read from it
- [ ] Props are typed with `PageProps<"/route">` / `LayoutProps<"/route">`
- [ ] Route params are validated, with `notFound()` for malformed values
- [ ] The user ID comes from Clerk, never from `params` or `searchParams`
- [ ] Data is fetched via `src/data/` helpers, scoped to the logged-in user
